# Type contracts

This repo has no tests, so the compiler and the linter are the only things that
check it before a push to `main` deploys it. Two gates do that work. Keep them
at zero errors by fixing the code, never by silencing the gate: **a lint error
blocks the deploy**, and a silenced one ships a crash instead.

| File | Read it for |
| --- | --- |
| `references/learned.md` | This skill's log of corrections. Read it before starting; **where it disagrees with the body below, it wins.** Created on first use, so absent means nothing logged yet. |
| `references/decisions.md` | Which flags, rules and boundary designs were measured and adopted or declined, with counts and dates. Read it before proposing a new gate or questioning an old one. |

## The two gates

| Gate | Where | What it means in practice |
| --- | --- | --- |
| `noUncheckedIndexedAccess`, `noImplicitReturns` | `tsconfig.app.json` | `array[i]` and `record[key]` are `T \| undefined` |
| typed `no-unsafe-*`, `no-unnecessary-type-assertion` | `eslint.config.js`, `src/` only | no `any` may be assigned, returned, passed, called or read from |

`src/components/ui/` is generated by shadcn and exempt from the lint gate. Do
not fix lint there and do not widen the exemption to other folders.

## Fixing "possibly undefined"

Pick the fix that tells the truth about the value. A fallback that can never
run is fine for a constant; for real data, prefer a guard that renders the
honest state.

| Situation | Fix | Example in repo |
| --- | --- | --- |
| First or last of a list | `const [first] = list`, `list.at(-1)`, then guard | `weather-page.tsx` span, `about-shared.ts` `trackRows` |
| Component needs one item | Narrow in the parent, pass the item as a prop | `blog-page.tsx` `latest`, `post-page.tsx` `post` |
| Destructured `split()` or callback tuple | Destructuring default | `cron.ts` `[start = "", end]`, sliders `([next = value])` |
| Fixed-length constant | Literal tuple `as const`, or return `[...] as const` | `chart-utils.ts` `SCALE`, `wind-rose-chart.tsx` `polar` |
| Lookup in a `Record<string, T>` | Read once into a const, branch on it | `code-highlight.ts` `sentinel` |
| Parallel arrays indexed together | `?? fallback` at the read | `calendar-heatmap.tsx` legend colours |
| Hook component with nothing to show | `if (!item) return null` after the last hook | `professional-journey.tsx` |

Do not use `!`. It turns the compile error back into the runtime crash the flag
exists to prevent, and the next edit will not know the assumption was there.

The table holds the seven shapes the first pass met, not every shape there is. A
"possibly undefined" error that fits no row is a finding for the log, along
with the fix that worked.

## Boundaries: where untyped data gets in

Everything inside the app is typed. Data arrives untyped at exactly these
places, so that is where it gets checked, once, and everything downstream
trusts the type. A fifth way in is a finding for the log and needs its own
recipe here: a `fetch` whose JSON is read field by field (the JSON Explorer's
example loader only re-serialises it to text), a URL parameter that is parsed
rather than tested for presence, a second library that returns `any`.

**localStorage.** Read through `readStoredObject(key)` in `src/lib/browser.ts`.
It swallows missing, malformed and blocked storage and returns
`Record<string, unknown> | null`. Check each field and fall back to the default
per field, so one bad value does not discard the rest. Copy the shape of
`loadSettings()` in `browser-mockup-page.tsx`: `clamp()` for numbers,
`allowed.find((v) => v === saved[key]) ?? DEFAULT[key]` for unions (no cast
needed), `typeof` for strings. Never call `JSON.parse` on storage directly; it
returns `any` and needs its own try/catch.

**CSV in `public/data/`.** These files are swapped without a rebuild, so they
are the one input the build never sees. `weather-data.ts` parses rows as
`Partial<T>` and keeps a row only if a type-guard `filter` passes: `isIsoDate`
for `date`, `isNumber` for numerics, `includes` for bucket unions. Charts slice
`date` by position, so a new date-like column needs a format guard, not just
`typeof === "string"`. When adding a column, add it to the row type and to the
guard in the same edit, then confirm no real rows are dropped (see Verify).

**Other `JSON.parse`.** Annotate the result `unknown` and narrow it. The JSON
Explorer keeps user JSON as `unknown` all the way to the renderer; do the same.

**Library `any`.** When a library hands back your own data typed `any`, give it
a type on arrival with a narrow cast of only the fields you read, and say why:

```tsx
// Recharts types the datum it hands back as `any`.
(item?.payload as { name?: string } | undefined)?.name
```

`Object.entries(obj)` on an `object` yields `any` values; annotate the result
`[string, unknown][]`. A cast from `any` is acceptable here because the data is
ours; it is not acceptable for data from storage, a file or the network.

## Data contracts in `src/data/*.json`

JSON imports are typed by inference, so a renamed or missing field already
fails typecheck at the component that reads it. What the compiler cannot see is
two fields that must agree. When you find one, delete the redundant field and
derive it, rather than documenting a rule someone has to remember:
`professional-journey.tsx` reads the timeline year out of `dateRange`, which
replaced a stored `year` that had to be kept in sync by hand. Before deleting a
field, script a check that the derived value equals every stored value.

## Tightening further

Measure before adopting anything, because the count decides whether it is worth
it and every new error must reach zero before the push:

```bash
npx tsc -p tsconfig.app.json --noEmit --<flagName> 2>&1 | grep -c "error TS"
```

For a lint rule, add it to the typed block in `eslint.config.js` and run
`npm run lint`. Already measured and declined, so do not re-litigate without a
new reason: `exactOptionalPropertyTypes` (14 errors, all fights with shadcn and
React prop types), `noPropertyAccessFromIndexSignature` (style only),
`no-floating-promises` / `no-misused-promises` (13 sites of `void` noise, about
promises not types).

Those counts were measured on 2026-09-21 and are not constants: dependencies
and code move. `references/decisions.md` holds the record and wins over this
summary. If a re-measure disagrees with a recorded count, say so and add a
dated line under the entry rather than quietly replacing the number, because
the change is itself the finding. Every new adopt-or-decline goes there too.

## Verify

Run all four; Prettier is not part of lint and CI will not run it for you.

```bash
npm run format && npm run typecheck && npm run lint && npm run build
```

This is a loop, not a step: run it, fix what failed, run it again, until all
four exit 0 and lint prints no problems. Do not report done on a red gate. A
failure you cannot fix goes in the report with its output, never behind a
disable comment.

Then check the pages you touched in the preview (`preview_start` name
`website`, hash routes such as `#/visualizations/weather`). For a boundary
change, prove the guard rather than the happy path:

1. **Storage:** seed a hostile value, reload the tool, read back what it
   re-saved. Expect defaults for bad fields, kept values for good ones, clamped
   numbers. E.g. `localStorage.setItem("browser-mockup-settings",
   '{"width":"x","padding":9999,"frame":"evil","chrome":"light"}')`, and also
   try an array (`'[1,2]'`). Remove the seeded keys afterwards.
2. **CSV guard:** count rows the new guard would reject in the real files; it
   should be 0, and the weather page's "N days of readings" should not move.
3. **Console:** `read_console_messages` with `onlyErrors`, expect none.

Note that `innerText` reflects `text-transform: uppercase`, so match eyebrow
and meta text case-insensitively.

If a change adds a convention, update the Conventions section of `CLAUDE.md`
in the same change.

A red gate whose cause turns out to be a wrong instruction in this skill is two
jobs: fix the code, then log the instruction (see Improving this skill).

## Known gaps

What the code does not yet check and what this skill has not proved. None is a
reason to stop; each is a reason not to claim more than was shown.

- **`isIsoDate` checks the month, not the day.** `2024-02-31` and `2024-01-00`
  pass. The day is only printed (`formatAxisDate`, `formatDate`) or used as a
  lookup key (`calendar-heatmap.tsx`), never as an index. Whether a Met Éireann
  export can contain such a date is unmeasured.
- **`wind_rose.csv` has no date-format guard.** `aggregateWindRose` takes
  `datetime.slice(0, 4)` of any non-empty string as the year. A malformed row
  becomes a key in `windRoseByYear` that no year reads, since years come from
  the temperature rows, rather than a dropped row.
- **`socialLinks.json` `iconKey` is a free string.** A typo drops the icon
  silently: `ICONS[link.iconKey]` is guarded, not validated, and a JSON import
  widens literals to `string`, so a union type cannot catch it.
- **Post frontmatter is not validated.** `posts.ts` defaults a missing `title`,
  `date` or `summary` instead of failing, and a malformed `date` sorts wrongly
  and renders as written. It is build-time author content, so whether it should
  fail the build is the author's call.
- **Routes and nav are not linked at compile time.** Nothing ties an `App.tsx`
  route to its `navigation.ts` entry. Not built; add it if a route ever ships
  without its nav entry.
- **Typed lint has edges.** `components/ui/` is exempt by choice, and files
  outside `src/` such as `vite.config.ts` get no typed rules because the block
  is scoped to `src/`.
- **Never watched on a fresh task.** Written on 2026-09-21 from the session
  that did the work. Neither its triggering nor its Verify loop has been seen
  firing in a new session. The first observation is a log entry either way.

Closing a gap is a result: say what closed it and delete the entry.

## Improving this skill

One log, one record, and one file outside the skill. They are not
interchangeable.

**A convention every session must follow** (a new gate, a new boundary helper,
a rule about `src/data/`) goes in the Conventions section of `CLAUDE.md` in the
same change, as Verify says. `CLAUDE.md` loads every session and this skill
loads only when it triggers, so a rule that lives only here is a rule most
sessions never see.

**A decision** (a flag or lint rule measured and adopted or declined, where a
boundary helper lives, a field deleted in favour of deriving it) is not a
correction. Append it to `references/decisions.md`, dated, with the measured
count and the reason. That file is never cleared. When a decision is reversed,
mark the old entry `Superseded by <date>.` and add the new one below it.

**A correction to this skill** (a row of the fixes table that did not fit, a
boundary recipe that misled, a Verify step that proved nothing) goes in the log
rather than into this file mid-fix.

**Where it goes.** Append to `references/learned.md`. Create it if absent. Do
not rewrite the body of SKILL.md while chasing a red gate: you have one error's
evidence, the entry might be wrong, and an uncurated file drifts fast.

**What to log.** Only these four, and only once the evidence exists:

- A recipe here failed in practice: a fix from the table that did not typecheck
  or changed behaviour, a Verify step that passed while the page was broken, or
  a repo example that no longer shows its pattern. For the last, say which
  happened: the code was refactored away, or it never showed what this skill
  claims. They have different causes and different fixes.
- The author corrected something this skill told you.
- You needed something this skill should have carried and had to derive it: a
  way untyped data gets in that Boundaries does not list, a "possibly
  undefined" shape with no row, a library other than Recharts that returns
  `any`.
- A change passed both gates and was still wrong at runtime: a fallback that
  ran on real data, a guard that dropped valid rows, a cast that lied about a
  shape. Log what the gates could not see and which check would have caught it.
  This is the most valuable entry type here. The gates are the only tests this
  repo has, and an entry like this is the only way their blind spots get
  written down.

**What not to log.** Hypotheses you did not run. An error the fixes table
already covers. Conventions and decisions, which have their own homes above.
And before logging a rule as wrong, check `references/decisions.md` and
`CLAUDE.md`: the Recharts casts, the `?? "transparent"` legend fallback and the
`components/ui/` exemption all look like the shortcuts this skill forbids, and
all three are deliberate. A deliberate rule that seems wrong is a question for
the author, not a correction.

**No entry may weaken a gate.** Learned entries arrive mid-debugging, which is
exactly when a gate is most annoying. No entry and no curation pass may remove
`noUncheckedIndexedAccess` or `noImplicitReturns`, downgrade a `no-unsafe-*`
rule to `warn`, widen the `components/ui/` exemption, or bless `!`, `as any` or
an eslint-disable as a fix. If a gate is genuinely wrong for this repo, that is
the author's decision, recorded in `references/decisions.md`.

**Entry format.** Terse, dated, evidenced. Five lines is plenty. This one is
real and already folded into Verify; it is here for its shape:

    ### 2026-09-21 — a text match failed on a page that was fine
    Checking the post page by its text, `innerText.includes("Next in the
    index")` returned false on a working post: the eyebrow is uppercased by CSS
    and `innerText` reflects that.
    Evidence: the same check as `/next in the index/i` returned true.
    Proposed: Verify should say to match eyebrow and meta text case-insensitively.

When an entry overturns an earlier one, open it with `Supersedes: <date> —
<claim>` and add `Superseded by <date>.` under the earlier heading. Curation
folds the later entry and drops both.

**Curation.** When asked, when the log passes ~20 entries or ~150 lines, when
its oldest entry is three weeks old, or once it is longer than this file, do a
pass: read `references/learned.md`, fold each confirmed entry into the section
where someone would look for it (a new table row, a new boundary recipe, a new
Verify check), delete any Known gap the entries have closed, drop anything
stale or since contradicted, and clear the log. Keep this file under ~500
lines; past that, move the boundary recipes into `references/` rather than
writing less.

**The gate.** Curation changes what this skill tells every later session, so it
is a change like any other. `.claude/skills/` is tracked (the rest of `.claude`
is not), so make it on a branch, show the diff, and say what evidence drove
each line. Do not commit and do not merge unless asked: a push to `main`
deploys the site. Appending to the log or the decisions record needs no
ceremony.

**Confirmed, not suspected.** "`exactOptionalPropertyTypes` raised 14 errors on
2026-09-21" is a fact. "It would probably be clean after a shadcn update" is a
hypothesis, and belongs nowhere until someone runs the count. It is the same
standard as Verify, prove the guard rather than the happy path, aimed at this
file instead of at the code.
